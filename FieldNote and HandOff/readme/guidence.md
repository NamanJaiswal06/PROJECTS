# FIELDNOTE — Guidance (Senior-Mentor Voice, for the ML Engineer)

> How to think today. Read once at Hour 0, again at Hour 6, and again if you feel lost.

---

## 1. Your job in three sentences
You are the brain and the voice of FIELDNOTE. The full-stack teammate builds a beautiful, reliable product shell — your job is to make sure that when a technician speaks, the system *thinks with retrieved memory* and *speaks the answer naturally*. If the AI is dumb or robotic, no UI saves it. If the UI is rough but the AI is sharp and voice-first, judges notice.

## 2. The one-day mindset
- **Working beats clever.** A 70% tool-calling agent that demos is worth 10x a 99% agent that crashes at Hour 8.
- **Don't learn new frameworks.** Stay in TS, your LLM SDK, and the four providers (STT, LLM, Qdrant, Rime).
- **Cut features ruthlessly.** The hero demo is one compressor, one technician, one handoff. Everything else is decoration.
- **Timebox each subsystem.** If Rime is flaky after 30 min, ship without voice for a moment and use a fixed chime + on-screen text. Don't burn Hour 11 on it.

## 3. What "good" looks like at Hour 12
A judge watches the demo and thinks: *"That AI actually understood the technician's situation, found the right historical case, and explained it out loud — and the next technician got the context without re-asking."* That's the win. Not: *"It used four frameworks and three databases."*

## 4. Voice is a feature, not a wrapper
Rime must be in the **main interaction loop**, not a closing flourish. Every AI response in the hero demo should be spoken. If you only TTS the last sentence, judges will notice. Plan audio budget: a 5-minute demo at 80 words/reply ≈ 12 replies ≈ 12 Rime calls. Stay under 80 words/reply.

## 5. Qdrant must visibly change the answer
The fastest way to fail this requirement is to embed too much, return too little signal, and let the LLM guess. The fix:
- **Tight embeddable text.** Concatenate `symptom. finding. action. status.` for incidents. Don't embed the whole Mongo document.
- **Filter on payload.** If equipmentId is known, hard-filter to that equipment's history. Otherwise the LLM gets cross-equipment noise.
- **Force the LLM to cite.** In the system prompt: *"If retrieved cases are provided, reference them by saying 'N similar cases show…'."* Judges hear this and instantly understand Qdrant's role.
- **Show the hits in the UI.** Even a small "Based on: Case #102, Case #087" line in the inspection screen is proof.

## 6. Tool calling > prompts
- Define 6 tools. Not 20.
- Each tool's input is a Zod schema. The LLM hallucinates less when constrained.
- `recordObservation` and `createHandoff` are the only two that **write** — `recordObservation` writes a field-log entry, `createHandoff` writes the end-of-session summary, and every other tool is read-only. Keep write surfaces small.
- After a write, **echo the structured result back into the conversation** so the next user turn is grounded.

## 7. The handoff is the product
A handoff is not just one blob of text. It is a structured object built from the session's field-log entries and a concise summary object with `checked`, `found`, `fixed`, `unresolved`, `next_steps`, and `similar_cases`. The summary is generated by the LLM from the session's observations and then embedded/indexed in Qdrant. This is what makes the next technician's "What happened with UNIT-27?" answer accurate. **If the handoff is sloppy, the recovery demo fails. If the recovery demo fails, you lose 30% of the score.**

## 8. Latency budget
A believable voice exchange:
- STT: 300–700 ms
- LLM first token: 400–800 ms
- Tool calls (Qdrant + Mongo): 200–500 ms
- Rime synthesis: 600–1500 ms
- Network + playback: 100–300 ms
- **Total: ~1.6–3.8 s**

If you're at 6+ s, the demo feels broken. Mitigations:
- Stream STT (Deepgram supports this).
- Don't synthesize a 200-word answer. Edit the system prompt to keep replies under 80 words.
- If Rime is slow, start playback as soon as the first audio chunk arrives, not the full buffer.

## 9. Common failure modes (and the fix)
- **"The agent keeps calling the wrong tool."** → Add a one-line tool description in plain English. Don't trust the schema name alone.
- **"Qdrant returns noise."** → Check embedding text quality. Re-rank by recency. Add a hard filter on `equipmentId` when known.
- **"Rime sounds off."** → Test the voice in isolation first. Some voices mumble technical terms. Spell out "UNIT-27" as "Unit 27" in TTS text.
- **"STT mistranscribes 'UNIT-27'."** → Add a small post-processing step that maps "unit twenty seven" / "unit 2 7" → "UNIT-27" before the agent sees it.
- **"The LLM invents equipment IDs."** → System prompt: *"Only use equipment IDs from the current session or the retrieved cases. Never invent."* Validate with a Zod enum.
- **"Mongo writes are malformed."** → Zod on every structured write. Reject and ask the LLM to retry with a feedback message.

## 10. Interruption/recovery — the 80/20
You will not get this perfect in one day. The 80/20 version:
- Mic is always-on when the system is in `SPEAKING` or `LISTENING` state.
- Any new STT final transcript cancels the in-flight audio (client side) and triggers a new agent turn.
- The new turn's system prompt gets a one-line suffix: *"The user interrupted. Answer only what they asked, in one sentence."*

That's it. 30 minutes of work, real feature, real wow factor on stage.

## 11. How to coordinate with the full-stack teammate
- **You define the tool API. They implement the HTTP handlers.** Write `tools/*.ts` with a clean `input → output` contract. They wrap it in `POST /api/incidents`, etc.
- **You own WebSocket message shapes.** Send a single document: `{ type, payload }`. They consume.
- **You share one `.env`.** Keys: `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, `DEEPGRAM_API_KEY`, `RIME_API_KEY`, `QDRANT_URL`, `QDRANT_API_KEY`, `MONGODB_URI` (theirs).
- **Don't fight over files.** You stay in `/server/src/ai/**`. They stay in `/client/src/**` and `/server/src/routes/**`.

## 12. When you're stuck
1. Sanity-check the smallest piece. STT alone. TTS alone. Qdrant alone. Always one variable at a time.
2. Read the actual error, not your assumption about it. Print full request/response.
3. Ask: is this a provider problem or a logic problem? Provider problems are usually key/format. Logic problems are usually prompt/schema.
4. If you're > 30 min stuck on something non-critical, cut it. The hero demo does not need it.
5. If the hero demo breaks, revert to the last working commit and reschedule the lost time.

## 13. The final hour
- Stop coding by Hour 10:30.
- Rehearse the demo out loud twice. The first run finds missing context, the second finds rough edges.
- Record a backup screen capture during rehearsal 2.
- Update the README's "How it works" with the actual architecture you shipped, not the one you planned.
- Sleep is not optional if the hackathon extends. Diminishing returns hit hard after Hour 10.

## 14. The single most important sentence
**"The next technician should not have to start from zero."**
Every design decision you make today, ask: does this make that sentence more true? If yes, ship it. If not, cut it.
